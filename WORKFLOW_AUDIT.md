# WORKFLOW AUDIT

## Scope and source

`workflow_detail.md` dan `project_context.md` tidak ditemukan di repository. Audit ini memakai workflow yang diberikan pada task sebagai source of truth sementara. Tidak ada kode yang diubah sebelum audit ini dibuat.

| Requirement | File terkait | Current implementation | Expected behavior | Result | Masalah | Recommended fix |
|---|---|---|---|---|---|---|
| Order lifecycle | `orders` migration, `OrderStatus`, `OrderService` | Satu `orders.status`: `WAITING_PROCESS`, `WAITING_PACKING`, `PACKING_COMPLETED`, `COMPLETED` | Order boleh memiliki banyak package dengan progress independen | **FAIL** | State package tidak ada; satu package dapat memindahkan seluruh order | Tambahkan `order_packages` dengan state package dan derive/order aggregate secara konservatif |
| Package data and partial shipment | `Order`, `OrderItem`, `PackingController`, `OrderPackagesModal` | UI membentuk package sementara, backend belum menyimpan assignment | Allocation per package tersimpan dan sisa item tetap tersedia | **FAIL/RISK** | Package configuration dikirim ke endpoint yang tidak tampak menyimpan package-level entity; tidak ada allocation table | Simpan package dan item allocations dalam transaction; validasi total allocation tidak melebihi quantity |
| Document printing | `DocumentPrintingPage`, `PackingService`, migrations | Print flags disimpan di React local state; backend tidak memiliki print action | `nota_printed` dan `label_printed` independen; complete hanya jika keduanya true | **FAIL** | Refresh/user lain kehilangan state; salah satu print dapat dianggap lengkap di UI | Tambahkan flags/timestamps per package dan endpoint idempotent untuk print nota/label |
| Reprint | `DocumentPrintingPage` | Tombol reprint hanya berdasarkan local state | Reprint tetap tersedia sampai/selama foto belum ada | **RISK** | Tidak persist dan tidak dijamin authorization/backend | Backend action idempotent; UI menampilkan ulang selama package accessible dan photo belum ada |
| Waiting photo | `packing_images`, `PackingService` | Image terikat ke `order_id`; upload mengubah order | Foto tersimpan per package | **FAIL** | Foto global dan satu upload menyelesaikan seluruh order | Tambahkan `order_package_id`; upload hanya mengubah package target |
| Photo transition | `PackingService` | Semua order menjadi `PACKING_COMPLETED` | A masuk resi, B/C tetap waiting photo | **FAIL** | Partial transition mustahil | Derive package state dari flags/photo/tracking |
| Sales read-only workflow | `OrderPolicy`, order resources, dashboards | Sales dapat melihat order; package progress belum API-backed | Sales dapat melihat/download foto, tidak dapat mutate packing | **FAIL/RISK** | Tidak ada package/photo authorization path; frontend-only workflow | Policy package/order + dedicated read endpoint; Admin-only mutations |
| Resi | `OrderService::completeShipment`, `OrderController` | Resi dan completed fields ada di order | Resi dan completed per package; package lain tidak ikut selesai | **FAIL** | Shipment locks whole order and requires order-level status | Add package shipment endpoint; derive order completed only when all allocated packages complete, preserving partial remainder |
| Document queue order | `PackingController::queue`, document UI | Queue filters order status and uses `latest()`/local ordering | Oldest package waiting in queue first | **FAIL** | `latest()` reverses FIFO; no queue-entry timestamp | Query package queue by `waiting_*_at ASC`, id ASC |
| Notification counter | `AdminDashboard`, `NotificationController` | Dashboard attempts sub-package expansion in frontend; notifications are order-level records | Count eligible packages exactly once | **FAIL/RISK** | Counter cannot be authoritative without persisted package state; notification records can double count | Count package query server-side and expose metric; do not count completed/non-eligible packages |
| Role permission | `OrderPolicy`, `UploadPackingImageRequest`, routes | Admin/owner approve/shipment; packing can upload; package configure route not visibly policy-protected | Admin does verify/configure/print/photo/resi; Sales read-only | **FAIL** | Packing role and owner behavior diverge from stated rule; configure/upload target lacks explicit Gate in shown controller | Add explicit package policies/FormRequests and backend authorization; frontend hiding is secondary |
| Race/duplicate action | `OrderService`, `PackingService` | Order approve/shipment use transactions; photo creates a new row every time | Duplicate clicks are safe/idempotent | **RISK** | Photo can duplicate; print has no backend state; shipment is order-level | Lock package row, unique/idempotent state updates, validate transitions in transaction |
| Security | routes/controllers/requests/policies | Sanctum and file MIME/size validation exist; public `/run-migrate` route exists | All mutations authorized; files scoped; no public admin operation | **RISK** | `/run-migrate` is unauthenticated; show policy permits any sales order; package IDOR not possible to check because entity absent | Remove/protect migration helper, enforce ownership/access, scope package/photo queries by order and policy |
| API/query freshness | `orderService`, React query pages | Some query invalidation exists, but print state is local and upload endpoint mismatch exists in client service | Mutations invalidate/refetch all affected queues and sales views | **FAIL** | `uploadPackingProof` client calls `/orders/{id}/packing-proof`, route is `/packing/{id}/upload-proof`; local print state is stale | Align endpoint; invalidate order/package/queue/dashboard queries after mutations |
| UI state | `DocumentPrintingPage`, `PackingQueuePage`, dashboards | Existing UI has package cards but derives them from order/items and local state | UI reflects backend package state without redesign | **FAIL** | Visual cards can suggest unsupported persistence | Keep design; replace derived/local state with API package fields |

## Initial trace

`POST /orders` -> `OrderService::createOrder` -> `orders.status=WAITING_PROCESS` -> approve updates whole order -> packing upload writes `packing_images.order_id` and sets whole order `PACKING_COMPLETED` -> shipment writes tracking/completed fields on whole order. There is no persisted package state between these transitions.

## Audit decision

The minimum safe fix is additive: introduce package and allocation persistence, move print/photo/shipment transitions to package scope, retain order fields/status as an aggregate/backward-compatible projection, and enforce all mutation authorization in backend policies/requests. A frontend-only patch would not satisfy the workflow or security requirements.
